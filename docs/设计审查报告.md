## 2. P0 阻塞性问题：版本与 DeepSeek 接入

### P0-1 思考模式与 Tool Calling 冲突（最高优先级）

**问题**

Agent 设计.md 全文未提及 DeepSeek 的思考模式，而 DeepSeek 当前模型默认开启思考模式且 reasoning_effort 默认为 high。

**原因**

DeepSeek 官方文档明确规定：

> 携带了 `tools` 参数的请求，在后续所有请求中，必须完整回传 `reasoning_content` 给 API——即使该轮模型未实际进行工具调用。若您的代码中未正确回传 `reasoning_content`，API 会返回 400 报错。

Tool Calling 天然是多轮交互（工具执行结果需要回传给模型），因此该约束必然触发。

经逐行比对 Spring AI 两个版本线的源码，实际支持情况如下：

| 能力 | Spring AI 1.1.8 | Spring AI 2.0.1 |
|---|---|---|
| `DeepSeekChatOptions` 支持 thinking 开关 | 无此字段 | 支持 `Thinking.ENABLED / DISABLED` |
| `DeepSeekChatOptions` 支持 reasoningEffort | 无 | 支持 `LOW / HIGH / MAX` |
| 响应中提取 reasoning_content | 支持 | 支持 |
| 请求中回传 reasoning_content | 不支持（只接收不回传） | 支持（`DeepSeekAssistantMessage` 完整往返） |
| 内置模型枚举 | `deepseek-chat` / `deepseek-reasoner`（均已退役） | `deepseek-v4-flash` / `deepseek-v4-pro` |

源码依据：

- 1.1.x 的 `DeepSeekChatModel.java` 仅在生成响应时提取 reasoningContent，仅处理 prefix 逻辑，没有回填请求的代码路径
- 2.0.x 的同一文件存在 `instanceof DeepSeekAssistantMessage` → 取出 reasoningContent → 写回请求的完整链路

**附加影响**

- 思考模式下 `temperature`、`presence_penalty`、`frequency_penalty` 参数不生效（官方说明：设置不会报错，但也不会生效）。所有依赖 temperature 控制结构化输出稳定性的设计都会失效。
- 思维链内容计入输出 token 并计费，成本约翻倍。

**建议方案（三选一，必须先做 PoC 实测）**

| 方案 | 做法 | 评价 |
|---|---|---|
| A（推荐） | 升级到 Spring AI 2.0.1，显式设置 `Thinking.DISABLED`，用非思考模式执行 Tool Calling | 协议约束随之解除，支持完整 |
| B | 保留 1.1.8，改用 OpenAI 兼容通道接入，通过 `OpenAiChatOptions.extraBody` 传 `{"thinking":{"type":"disabled"}}` 关闭思考模式 | `extraBody` 字段在 1.1.x 确实存在，但此路径未经实测，必须在初始化前验证 |
| C | 保留 1.1.8 且不关闭思考模式 | 不可行，工具调用第二轮必然返回 400 |

### P0-2 配置前缀过时

**问题**

Agent 设计.md 第 7 节的配置示例使用 `spring.ai.openai.*` 前缀。

**原因**

Spring AI 已提供 DeepSeek 原生 starter（`spring-ai-starter-model-deepseek`，自 1.0.0-RC1 起全版本线可用，Maven 中央仓库可查证），配置前缀为 `spring.ai.deepseek.*`，并提供 `DeepSeekChatModel`、`DeepSeekChatOptions` 原生类型。继续使用 OpenAI 兼容通道会丢失 DeepSeek 专有参数（thinking、reasoning_effort），而这些参数正是 P0-1 的解法所在。

**建议**

文档中写定接入方式，配置示例修正为：

```yaml
spring:
  ai:
    deepseek:
      api-key: ${DEEPSEEK_API_KEY}
      base-url: https://api.deepseek.com
      chat:
        options:
          model: deepseek-flash
```

### P0-3 模型名缺失且默认值已失效

**问题**

四份文档均未指定具体模型名，仅保留 `${DEEPSEEK_MODEL}` 占位符。

**原因**

DeepSeek 官方当前（2026-10-09）模型列表只有两个：

| 模型名 | 底层版本 | 上下文长度 | 价格（空闲时段，元/百万 token） |
|---|---|---|---|
| `deepseek-flash` | DeepSeek-V4.1-Flash | 1M | 输入 1，输出 4 |
| `deepseek-v4-pro` | DeepSeek-V4-Pro-0813 | 1M | 输入 4.5，输出 13.5 |

`deepseek-chat` 和 `deepseek-reasoner` 已从官方文档中消失；`deepseek-v4-flash` 亦已下线（请求会转发至 V4.1-Flash）。而 **Spring AI 1.1.8 的默认模型名恰为 `deepseek-chat`**，不显式配置就会请求一个已退役的模型名。

**建议**

文档中写定：`model` 必须显式配置为 `deepseek-flash`（毕业设计场景够用且成本低），禁止依赖 Spring AI 默认值。

**问题**

系统架构设计.md 第 2 节仅写"与当前 Spring Boot 版本兼容的 Spring AI 版本"，未落到具体版本号，容易在初始化时随手套用一个来路不明的教程版本。

**原因**

Spring AI 与 Spring Boot 存在硬性兼容矩阵，且 Spring 生态的支持周期已发生重要变化：

| 组件 | 版本 | 对应 Spring Boot | Java 基线 | 支持状态 |
|---|---|---|---|---|
| Spring AI | 1.1.8（1.1.x 末版） | 3.5.x | 17 | 1.1.x 线已停止新增功能 |
| Spring AI | 2.0.1 | 4.0.x / 4.1.x | 17（构建需 JDK 21） | 当前主线 |
| Spring Boot | 3.5.16 | — | 17 | **OSS 支持已于 2026-06-30 结束** |
| Spring Boot | 4.0.8 / 4.1.1 | — | 17（推荐 21） | 4.0.x OSS 支持至 2026-12-31 |

Spring Framework 6.2、Spring Security 6.5 与 Spring Boot 3.5 同期结束 OSS 支持。

**建议**

在系统架构设计.md 中写死版本表，见下节推荐组合。

### 版本选型推荐

| 项目 | 方案甲（推荐） | 方案乙（保留 Java 17 生态） |
|---|---|---|
| Spring Boot | 4.1.1 | 3.5.16（最后一个 OSS 版本） |
| Spring AI | 2.0.1 | 1.1.8 |

**无论选择哪个方案，初始化前必须完成 PoC**：一个最小 Spring Boot 工程 + 一个 `@Tool` 方法，跑通"用户提问 → 模型调用工具 → 结果回传 → 模型作答"的完整闭环。这是唯一能终结 P0-1 不确定性的手段。

## 3. P1 文档间冲突

### P1-1 文件类型错误的 HTTP 状态码自相矛盾

- 系统架构设计.md 第 8 节：文件格式不支持 → 400
- API 接口设计.md 第 1 节：415 | 41500 | 文件类型不支持

**建议**：统一为 415（语义更准确），同步修改系统架构设计.md。另需注意 Spring 的 `MaxUploadSizeExceededException` 默认返回 500，必须在全局异常处理器中映射为 413。

---

### P1-2 分析失败是否入库，两份文档取向相反

- 系统架构设计.md 第 8 节：AI 输出无法解析 → 不保存无效结果
- 数据库设计.md：`resume_analysis` 设计了 `status`（SUCCESS/FAILED）与 `error_message` 字段

**建议**：定死其中一种。推荐只保存成功结果（与架构文档一致），保留 `status` 字段以备扩展，失败信息仅记录脱敏日志。若选择保存失败记录，必须明确对应的 API 返回结构。

---

### P1-3 岗位分析的"过期"标记无处落地

**问题**

API 接口设计.md 第 5.4 节要求"岗位描述更新后，旧岗位分析应标记为过期或生成新的分析版本"，但 `job_analysis.status` 的取值仅有 `SUCCESS/FAILED`，没有 STALE/EXPIRED。

**原因**

这不只是缺少一个状态值。同一缺口还影响：

- Agent 设计.md 4.3："如果岗位内容未变化且已有成功分析，可以复用已有结果"
- Agent 设计.md 4.2："优先返回最新成功分析"

判断"内容未变化"需要内容指纹，而该字段不存在。

**建议**

为 `resume_analysis` 和 `job_analysis` 各增加一列：

```sql
source_hash VARCHAR(64) DEFAULT NULL COMMENT '分析所依据原文的 SHA-256，用于判断能否复用'
```

复用判断与过期标记均依赖此字段，无需新增状态值。

---

### P1-4 Agent 会话列表没有数据支撑

**问题**

API 接口设计.md 第 8.2 节定义了 `GET /api/agent/sessions` 返回会话列表，但数据库中**没有会话表**，仅有 `agent_chat_message` 依靠 `session_id` 字段聚合。

**原因**

会话列表至少需要展示标题与时间。当前只能 `GROUP BY session_id` 取首条消息作为标题，缺少会话级元数据，分页排序也难以实现。

**建议**

新增会话表：

```sql
CREATE TABLE agent_session (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  user_id BIGINT NOT NULL,
  session_id VARCHAR(64) NOT NULL,
  title VARCHAR(100) NOT NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY uk_agent_session_sid (session_id),
  KEY idx_agent_session_user (user_id, updated_at),
  CONSTRAINT fk_agent_session_user FOREIGN KEY (user_id) REFERENCES sys_user(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='智能体会话';
```

### P1-5 面试题目数量存在双份来源

- 创建会话时传 `questionCount`，落库 `interview_session.question_count`
- 单独的生成题目接口又传 `count`

**建议**：明确语义。`question_count` 表示"计划生成数"；生成接口的 `count` 应删除或明确定义为覆盖值。推荐做法是**创建会话时一次性生成全部题目**，删除独立的题目生成接口，减少状态组合。

### P1-6 删除策略三份文档互相推诿

- 系统架构设计.md：删除简历时**明确**是否同步删除原文件和关联分析数据
- 数据库设计.md：第一版**建议**逻辑删除；如果采用物理删除，需**明确**规则
- API 接口设计.md：按项目**确定**的逻辑删除策略处理

三份文档都在要求"明确"，但没有一份明确。此外 `resume_analysis` 表没有逻辑删除标记字段，即使定了逻辑删除也无处落笔。

**建议（可直接采用）**

- 物理文件同步删除
- `resume_analysis` 的可见性依赖父表 `resume.status` 判断，不单独加字段

### P1-7 Agent 工具方法签名与其安全声明冲突

Agent 设计.md 4.1 的示意代码：

```java
public ResumeAnalysisResult analyzeResume(Long resumeId, Long currentUserId)
```

紧随其后的安全说明却写明："不建议让模型自由传入 `currentUserId`，用户 ID 应由服务端认证上下文注入。"

**问题**：在 Spring AI 的 `@Tool` 机制下，方法参数会被自动解析为工具的 JSON Schema，`currentUserId` 将**成为模型可见、可填写的参数**，与安全声明直接冲突。

**建议**：改为只接收 `resumeId`，用户身份从安全上下文获取：

```java
@Tool(description = "分析当前用户指定的一份简历")
public ResumeAnalysisResult analyzeResume(@ToolParam(description = "简历ID") Long resumeId) {
    Long userId = CurrentUser.id();   // 从安全上下文获取，模型无法干预
    // ...
}
```

## 4. 数据库设计审查

**总体结论：DDL 语法本身没有错误**，可在 MySQL 8 直接执行。外键声明顺序正确、类型匹配、字符集与排序规则合规、JSON 字段用法合法。问题集中在字段完整性、索引设计与业务文档的一致性上。

### 4.1 字段缺口

| 表 | 缺口 | 影响 | 关联问题 |
|---|---|---|---|
| `resume_analysis` / `job_analysis` | 缺 `source_hash` | 无法判断分析结果能否复用 | P1-3 |
| `interview_session` | 缺 `updated_at` | 违反文档自定约定 | P1-9 |
| `interview_question` | 缺 `updated_at` | 同上 | P1-9 |
| `resume_analysis` | 无逻辑删除标记 | 与逻辑删除策略冲突 | P1-6 |
| `interview_question` | `sort_order` 无唯一约束 | 同会话内序号可能重复 | — |

### 4.2 索引问题

1. **索引冗余**：`resume_analysis` 同时存在 `uk_resume_analysis_version(resume_id, version_no)` 与 `idx_resume_analysis_resume_created(resume_id, created_at)`，前缀重复。按时间排序可直接使用 `version_no` 替代，`idx_*_resume_created` 价值有限。`job_analysis` 同理。

2. **外键索引未显式声明**（MySQL 会自动补建，但不应当依赖隐式行为）：
   - `match_record` 的 `fk_match_job`、`fk_match_resume_analysis`、`fk_match_job_analysis`
   - `interview_session` 的 `fk_interview_job`

3. **外键删除行为未声明**：当前均为隐式 `RESTRICT`。若最终采用物理删除策略，会因外键约束而失败。应显式写出 `ON DELETE RESTRICT` 并说明理由。

4. **时间精度**：`DATETIME` 为秒级精度，在多版本分析场景下可能产生排序并列。推荐直接使用 `version_no` 排序（零成本），或分析表改用 `DATETIME(3)`。

### 4.3 其他

- 数据库名 `job_assistant` 与项目名 `career-pilot-ai` 不一致，建议统一为 `career_pilot`，保证论文与文档的一致性。
- JSON 字段在 MyBatis-Plus 下需要显式配置 `JacksonTypeHandler`（`@TableField(typeHandler = ...)`），文档中应注明，否则实现时必然踩坑。

### 10.3 依赖分析（X-1）及上一轮结论更正

**上一轮报告有误，此处更正**：上一轮称"Spring Boot 4.1.1 不再管理 Jackson 2"，该结论不准确。实测 `spring-boot-dependencies:4.1.1` 的 POM：**同时导入 `com.fasterxml.jackson:jackson-bom:2.21.5`（Jackson 2）与 `tools.jackson:jackson-bom:3.1.5`（Jackson 3）**。

由此 X-1 的实际结论变为：

| 项 | 结论 |
|---|---|
| Jackson 引入路径 | `jjwt-jackson` 是显式依赖，`jackson-databind` 是其**传递依赖** |
| jjwt 声明的版本 | 从 `jjwt-root:0.12.7` 继承，为 **2.12.7.1**（2022 年版本） |
| Spring Boot 是否提供合适版本 | **是**。依赖管理会将其提升为 2.21.5 |
| 处理建议 | **不手动覆盖版本**，使用 Spring Boot 管理的版本；工程创建后用 `mvn dependency:tree` 确认（V7） |
| 残留说明 | Boot 4.1.1 管理的 2.21.5 与 3.1.5 在 2026-09 披露的若干公告中仍处受影响区间（修复版本 2.21.7+/3.1.7+）；跟随 Spring Boot patch 升级是官方路径 |

上述"会被提升为 2.21.5"属**依据依赖管理规则的推断，尚未在本项目实测**，因此当时列为 V7 验证项、未标记为已解决。

**V1.3 更新（2026-10-09）**：已实测确认 —— `mvn dependency:tree -Dincludes=*jackson*` 显示 `jackson-databind` 解析为 **2.21.5**，且 Jackson 2（`com.fasterxml.jackson.*`，2.21.5）与 Jackson 3（`tools.jackson.*`，3.1.5）共存，与本表结论完全一致，**无需手动覆盖**。V7 就此关闭。
