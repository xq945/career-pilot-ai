## 1. 测试加载应用上下文失败：DeepSeek API Key 缺失

### 现象

依赖解析与编译均通过后，`mvn package` 在测试阶段失败：

```text
[ERROR] CareerPilotApplicationTests.contextLoads ? IllegalState
        Failed to load ApplicationContext
Caused by: org.springframework.beans.BeanInstantiationException:
        Failed to instantiate [org.springframework.ai.deepseek.DeepSeekChatModel]
Caused by: java.lang.IllegalArgumentException: DeepSeek API key must be set
    at ...DeepSeekChatAutoConfiguration.deepSeekApi(DeepSeekChatAutoConfiguration.java:94)
```

### 根因

Spring AI 的 `DeepSeekChatAutoConfiguration` 在装配 `DeepSeekChatModel` 时**强制要求 `spring.ai.deepseek.api-key` 存在**，缺失即抛异常。本项目引入了 `spring-ai-starter-model-deepseek`，该自动配置无条件参与装配，导致测试上下文无法启动。

这属于**预期的安全约束**而非缺陷：API Key 是运行时配置，本就不应写入仓库（《系统架构设计》7、9 节）。

### 解法

在**测试专用配置** `src/test/resources/application.yml` 中提供占位值：

```yaml
spring:
  ai:
    deepseek:
      # 占位值：仅为让 DeepSeekChatAutoConfiguration 完成装配，
      # 测试不发起真实模型调用，因此无需真实密钥，也不应写入真实密钥。
      api-key: test-placeholder-key
```

该文件只作用于测试类路径，不影响生产配置；测试不发起真实模型调用，占位值不会被真正使用。

### 经验

**引入 AI 能力后，"没有密钥"本身就会导致应用上下文启动失败**，而不只是调用时失败。任何加载完整上下文的测试（`@SpringBootTest`）都会触发该校验。

同理，本地开发运行应用时，也必须在 `application-local.yml`（已被 `.gitignore` 忽略）中配置真实密钥，否则应用无法启动 —— 这一点在开始写业务代码前就应知道，否则容易误判为代码问题。

## 2. 测试数据源：用 H2 内存库替代本机 MySQL

### 现象

引入 `mybatis-plus-spring-boot4-starter` 后，classpath 上存在 DataSource 相关自动配置。若不加处理，任何 `@SpringBootTest` 都会因找不到数据源配置而启动失败（`Failed to configure a DataSource: 'url' attribute is not specified`）。

### 根因

持久层依赖存在时，Spring Boot 的数据源自动配置为**强制项**：要么提供可用的数据源配置，要么显式排除该自动配置。

### 解法

在 `src/test/resources/application.yml` 中配置 H2 内存库，并以 `MODE=MySQL` 对齐 MySQL 语法：

```yaml
spring:
  datasource:
    url: jdbc:h2:mem:careerpilot;DB_CLOSE_DELAY=-1;MODE=MySQL
    driver-class-name: org.h2.Driver
    username: sa
    password: ""
```

H2 以 `test` scope 引入，不进入生产依赖。

### 经验

**单元测试不应依赖本机 MySQL 是否启动、库表是否建好**，否则测试无法在他人机器和 CI 上运行。用 H2 内存库 + MySQL 兼容模式，是 MyBatis-Plus 项目里成本最低的做法。

需注意：`MODE=MySQL` 只对齐**语法**，不覆盖所有行为差异（如部分函数、类型语义）。若测试中出现只在 H2 上复现的怪异行为，应优先怀疑兼容模式覆盖不到的部分。
