## 1. Tika 4.1.0 依赖无法解析

### 现象

`mvn clean package` 在依赖解析阶段失败：

```text
[ERROR] Failed to execute goal on project career-pilot-server: Could not resolve dependencies
[ERROR] dependency: org.apache.tika:tika-parsers-standard-package:jar:4.1.0 (compile)
[ERROR] 	Could not find artifact org.apache.tika:tika-parsers-standard-package:jar:4.1.0
        in aliyun-central (https://maven.aliyun.com/repository/central)
```

### 排查过程

1. **初步误判**：以为是镜像同步滞后，查阿里云的 `maven-metadata.xml`，发现它**确实列出了 `4.1.0`**。
2. **推翻误判**：直接探测 jar 文件地址，返回 `404 Not Found`。
3. **关键一步**：改查中央仓库 `repo1.maven.org`，其 `4.1.0` 与 `4.0.0` 的 jar **同样 404** —— 说明与镜像无关。
4. **定位**：列出该版本在仓库中的目录内容，发现只有 `.pom` 与校验文件，**没有 `.jar`**：

```text
tika-parsers-standard-package-4.1.0.pom
tika-parsers-standard-package-4.1.0.pom.asc
tika-parsers-standard-package-4.1.0.pom.md5
tika-parsers-standard-package-4.1.0.pom.sha1
```

5. 读取该 pom，确认 `<packaging>pom</packaging>`，其聚合了 25 个子模块（`tika-parser-pdf-module`、`tika-parser-microsoft-module`、`tika-parser-ocr-module` 等）。

### 根因

**Apache Tika 从 4.x 起改变了该构件的发布形式**：`tika-parsers-standard-package` 由 3.x 的"单个完整 jar"变为"pom 类型的空聚合模块"，实际的解析能力拆分到各 `tika-parser-*-module` 子模块中。

对照：3.3.2 的目录下同时存在 `.jar`、`-sources.jar`、`-javadoc.jar`。

### 解法

**采用 Tika 3.3.2（3.x 末期稳定版）**，即 `pom.xml` 中的 `<tika.version>3.3.2</tika.version>`。

选择理由：

1. 该版本为单个完整 jar，依赖声明方式最标准，无需 `<type>pom</type>` 等特殊处理。
2. 依赖树更小 —— 4.x 的聚合方式会一次性引入 25 个子模块（含 OCR、音视频、CAD 等本项目用不到的能力）。
3. 规避二次失败风险 —— 25 个子模块中任意一个在镜像站同步不全，都会导致构建再次失败。
4. 本项目第一版只需 PDF / DOCX 文本提取（《系统架构设计》6.1），3.3.2 完全覆盖。

**若日后需要 Tika 4.x 的能力**，推荐按需依赖具体子模块，而非引入整个聚合包：

```xml
<dependency>
    <groupId>org.apache.tika</groupId>
    <artifactId>tika-parser-pdf-module</artifactId>
    <version>4.x.x</version>
</dependency>
```

### 经验

**Maven 仓库 metadata 中列出的版本号，不等于该版本存在可下载的构件。**

判断某个版本能否使用，应直接列出该版本的仓库目录，确认发布了哪些文件：

```bash
curl -s "https://repo1.maven.org/maven2/org/apache/tika/tika-parsers-standard-package/4.1.0/"
```

只有看到 `.jar`，才说明该构件可按默认方式（jar packaging）依赖。

另需注意：镜像站（如阿里云）可能只同步了 metadata 而未同步构件文件。此时即便中央仓库有 jar，走镜像的构建仍会失败 —— 本次若直接归因于"镜像滞后"并换仓库源，问题并不会解决。

## 2. 构建 JDK 版本与项目目标不一致

### 现象

本机默认 `JAVA_HOME` 指向 JDK 17：

```text
$ java -version
java version "17.0.20.1"

$ echo $JAVA_HOME
G:\develop\jdk\jdk17
```

而《系统架构设计》2.1 节选定的是 **Java 21**（Spring Boot 4.1.1 官方推荐 21）。

### 根因

本机安装了多个 JDK（`G:\develop\jdk\jdk17` 与 `G:\develop\jdk\jdk21`），默认环境变量指向 17，与项目目标版本不符。

### 解法

本机已装有 JDK 21（`G:\develop\jdk\jdk21`），无需额外安装。

**2026-10-09：已将系统级 `JAVA_HOME` 与 PATH 条目由 JDK 17 切换为 JDK 21。**

| 变量 | 修改前 | 修改后 |
|---|---|---|
| 系统级 `JAVA_HOME` | `G:\develop\jdk\jdk17` | `G:\develop\jdk\jdk21` |
| 系统级 PATH 首项 | `G:\develop\jdk\jdk17\bin` | `G:\develop\jdk\jdk21\bin` |

注意事项：

- 系统级环境变量存于 `HKEY_LOCAL_MACHINE`，**修改需管理员权限**。
- **环境变量变更对已打开的终端无效**，必须新开终端或重启 IDE 才能读到新值。这一条极易造成"明明改了却没生效"的误判。
- 修改前的完整 PATH 已备份至 `%USERPROFILE%\machine-path-backup-20261009.txt`，如需回退可比对恢复。

若某些场景仍需按项目隔离版本，命令行可临时覆盖：`JAVA_HOME=/g/develop/jdk/jdk17 mvn ...`。

### 经验

多 JDK 环境下有两种做法，各有取舍：

1. **项目级指定** —— 命令行用环境变量前缀临时覆盖，IDE 用项目 SDK 设置。不动全局配置，各项目互不影响，但每次构建都要带上前缀，容易遗漏。
2. **全局切换** —— 一次改好，所有工具（Maven、Gradle、命令行）统一使用新版本。代价是依赖旧版本的其他项目会受影响。

本项目采用第 2 种。若日后出现"某个老项目构建突然报 Java 版本错"，应首先怀疑这次全局切换。

## 附：V7 验证结论（依赖解析实测）

按《系统架构设计》第 11 节，V7 验证项结论如下：

| 项目 | 内容 |
|---|---|
| 验证项 | V7：jjwt 传递引入的 `jackson-databind` 实际解析版本 |
| 验证方式 | `mvn dependency:tree -Dincludes=*jackson*` |
| **结论** | **解析为 `2.21.5`，与设计预期一致，无需手动干预依赖管理** |

实测依赖树关键片段：

```text
+- org.springframework.boot:spring-boot-starter-web:jar:4.1.1:compile
|  \- org.springframework.boot:spring-boot-starter-jackson:jar:4.1.1:compile
|     \- org.springframework.boot:spring-boot-jackson:jar:4.1.1:compile
|        \- tools.jackson.core:jackson-databind:jar:3.1.5:compile        ← Jackson 3
+- org.springframework.ai:spring-ai-starter-model-deepseek:jar:2.0.1:compile
|  \- org.springframework.ai:spring-ai-client-chat:jar:2.0.1:compile
|     \- com.github.victools:jsonschema-generator:jar:5.0.0:compile
|        \- tools.jackson.core:jackson-core:jar:3.1.5:compile
\- io.jsonwebtoken:jjwt-jackson:jar:0.12.7:runtime
   \- com.fasterxml.jackson.core:jackson-databind:jar:2.21.5:compile     ← Jackson 2，被 Boot 提升
      +- com.fasterxml.jackson.core:jackson-annotations:jar:2.21:compile
```

由此确认《系统架构设计》2.4 节的两项论断均已实证：

1. jjwt 传递引入的 `jackson-databind` 被 Spring Boot 4.1.1 的依赖管理提升为 `2.21.5`，**未停留在 jjwt 自带的 2.12.7.1**。
2. Jackson 2（`com.fasterxml.jackson.*`，2.21.5）与 Jackson 3（`tools.jackson.*`，3.1.5）**共存，且版本与设计表格一致**。

其余验证项（V1–V6）涉及真实模型调用与数据库集成，**已在后续阶段完成并全部通过**，结论见《系统架构设计》第 11 节与《设计审查报告》第 9 节。
