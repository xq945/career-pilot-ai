## 1. 设计目标

本系统面向个人求职者，提供简历管理、岗位管理、简历与岗位匹配、AI 面试和求职智能体等功能。架构应满足本科毕业设计的可实现性、可维护性和可演示性。

设计原则：

1. 优先采用单体分层架构，不引入微服务。
2. 普通业务逻辑与大模型调用解耦。
3. AI 输出使用结构化对象校验后再保存。
4. 所有用户私有资源均执行当前用户归属校验。
5. 大模型 API Key 仅在后端配置，不下发到浏览器。
6. 第一版不依赖 Redis、向量数据库、RAG、多智能体或招聘网站爬虫。

### 2.2 版本兼容性依据

**【已核实】** 以下对应关系经 Spring AI 官方 README 兼容矩阵与 Maven 中央仓库实际发布版本核对：

| 组件 | 版本 | 兼容的 Spring Boot | Java 基线 | 状态 |
|---|---|---|---|---|
| Spring AI | 1.1.x（末版 1.1.8） | 3.5.x | 17 | 已停止新增功能 |
| **Spring AI** | **2.0.1** | **4.0.x / 4.1.x** | 17（构建需 JDK 21） | **本项目采用，当前主线** |
| Spring AI | 2.1.x | — | — | 里程碑版，不采用 |
| Spring Boot | **4.1.1** | — | 17（官方推荐 21） | **本项目采用** |
| Spring Boot | 3.5.16 | — | 17 | OSS 支持已于 2026-06-30 结束，不采用 |

选择依据：**Spring AI 2.0.x 是唯一完整支持 DeepSeek 思考模式控制与 `reasoning_content` 回传的版本线**，而 DeepSeek 当前模型默认开启思考模式，该能力直接决定 Agent Tool Calling 能否跑通。详见第 6.3 节与 Agent 设计文档。

### 2.3 Spring Boot 4 带来的变化（【已核实】，实现时必须注意）

1. **Jackson 3 成为首选 JSON 库**：包名由 `com.fasterxml.jackson` 迁移到 `tools.jackson`。自定义序列化、反序列化代码及第三方库集成需按 Jackson 3 的包名编写。
2. **模块化拆分**：Spring Boot 4 将原先的大 jar 拆分为更细粒度的模块。`spring-boot-starter-web` 仍然可用（其内部聚合了 `spring-boot-starter-jackson`、`spring-boot-starter-tomcat`、`spring-boot-webmvc`）。
3. **空值注解变更**：不再支持 `javax.annotations.NonNull` 与 `org.springframework.lang.Nullable`，改用 JSpecify 注解。

> 版本管理规则：不要随意混用不同 Spring AI 教程中的依赖版本。创建项目时，先根据 Spring Boot 版本选择兼容的 Spring AI BOM，并以实际依赖解析结果为准。

### 2.4 依赖管理与 Jackson 版本说明

**【已核实】** Spring Boot 4.1.1 的依赖管理**同时覆盖 Jackson 2 与 Jackson 3**：

| BOM | 包名前缀 | Boot 4.1.1 管理的版本 |
|---|---|---|
| `com.fasterxml.jackson:jackson-bom` | `com.fasterxml.jackson.*`（Jackson 2） | 2.21.5 |
| `tools.jackson:jackson-bom` | `tools.jackson.*`（Jackson 3） | 3.1.5 |

**前提要求**：项目必须通过 `spring-boot-starter-parent` 或 `import spring-boot-dependencies` 使用 Spring Boot 的依赖管理。这是下方所有版本结论成立的基础。

**不在 Spring Boot 管理范围内的依赖**（版本必须自行指定，注意不要盲目指定）：

- `io.jsonwebtoken:jjwt-*`（JWT 库）
- `com.baomidou:mybatis-plus-spring-boot4-starter`（ORM）
- `org.apache.tika:tika-core` 及解析器模块（文本提取）

**关于 jjwt 引入的 Jackson 2（第二轮审查 X-1 项）**：

`jjwt-jackson` 会传递引入 `com.fasterxml.jackson.core:jackson-databind`。其自身 POM 中继承的版本是 **2.12.7.1**（2022 年版本，其后披露的多个漏洞修复均未包含）。但由于 Spring Boot 4.1.1 的依赖管理覆盖了 Jackson 2，**预期实际解析结果会被提升为 2.21.5**，无需手动覆盖。

处理原则：

1. **不要手动指定 Jackson 版本**。Jackson 2 的版本随 Spring Boot 的 patch 版本演进，手动覆盖会脱离官方验证组合。
2. 若需要更全面的依赖管理，可选用 `jjwt-bom`（0.12.7 起提供）统一管理 jjwt 各模块版本。
3. **【已核实】** 实际解析出的 `jackson-databind` 版本已于 2026-10-09 通过 `mvn dependency:tree` 确认：**解析结果为 2.21.5**（Spring Boot 管理值），未停留在 jjwt 自带的 2.12.7.1，**无需手动覆盖**（见第 11 节 V7）。
4. 已知情况说明：Boot 4.1.1 管理的 Jackson 2.21.5 与 Jackson 3.1.5 在 2026-09 披露的若干安全公告中同样处于受影响区间，修复版本为 2.21.7+ / 3.1.7+。**跟随 Spring Boot 的 patch 升级是官方路径**，本项目不应自行升级，但应在依赖审计时记录该状态。

**Jackson 2 与 Jackson 3 共存是被官方支持的**：Spring Boot 4 为此提供了 `spring-boot-jackson2` 模块，两者包名不同，不构成冲突。

## 3. 总体架构

```text
Vue 3 浏览器端
  ├─ 登录/注册
  ├─ 简历管理
  ├─ 岗位管理
  ├─ 匹配报告
  ├─ AI 面试
  └─ 求职智能体
         │ HTTPS/HTTP + JSON
         ▼
Spring Boot REST API
  ├─ Controller：参数接收、响应封装
  ├─ Service：业务规则与事务
  ├─ Security：JWT 认证、资源归属校验
  ├─ AI Service：Prompt、模型调用、输出校验
  ├─ Agent：任务理解、工具调用、结果整合
  ├─ Tool：封装可供 Agent 调用的业务能力
  ├─ Mapper/Repository：数据库访问
  └─ File Service：上传、校验、解析和存储
         ├─ MySQL
         ├─ 本地文件存储（项目目录之外）
         └─ DeepSeek API（由 Spring AI 调用）
```

## 4. 后端分层职责

### 4.1 Controller 层

- 定义 REST API。
- 校验请求格式和必填字段。
- 调用 Service，不直接写 SQL 或直接调用模型。
- 返回统一响应结构。
- 不信任前端传来的 `userId`；用户身份从认证上下文获取。

### 4.2 Service 层

- 执行业务规则。
- 校验资源归属。
- 管理事务和状态。
- 协调 Mapper、文件服务和 AI 服务。
- 对 AI 调用异常、超时和解析失败进行处理。

### 4.3 AI Service 层

- 构建 Prompt。
- 调用 Spring AI 的 ChatClient。
- 将模型输出转换为 DTO/结构化对象。
- 校验分数范围、字段完整性和数组长度。
- 不直接信任模型生成的 ID、权限或数据库操作指令。

### 4.4 Agent 与 Tool 层

- Agent 负责接收用户任务、选择可用工具并整合工具结果。
- Tool 只提供有限、明确的业务能力。
- Tool 通过当前认证用户上下文限制访问范围，**用户 ID 不得作为工具参数暴露给模型**（详见 Agent 设计文档 4.1）。
- 不向模型开放任意 SQL、任意文件路径或任意网络访问能力。
- Tool Calling 是模型提出工具调用请求，后端执行工具后把结果交还模型；工具本身的授权与参数校验由后端负责。

## 6. 核心业务链路

### 6.1 简历处理

```text
用户上传 PDF/DOCX
  → 校验扩展名、MIME、文件大小（并校验文件魔数）
  → 生成服务端随机文件名并保存
  → 提取文本
  → 检查文本非空且长度合理
  → 保存 resume 元数据与文本
  → 用户主动发起 AI 分析
  → Spring AI 调用 DeepSeek
  → 校验结构化输出
  → 保存 resume_analysis（含 source_hash）
```

约束：

- 单文件上限 10 MB（配置项，部署时可调整）。
- 提取文本上限 20000 字符，超长部分截断后再送入模型（控制成本并规避无效输入）。
- 扫描版 PDF 可能无法直接提取文本，第一版应提示用户上传可复制文本的 PDF，OCR 作为后续扩展。

### 6.2 岗位匹配

```text
用户选择简历和岗位
  → 校验两者均属于当前用户
  → 获取最新简历分析与岗位分析
  → 缺少分析结果时，按调用入口分别处理：
       REST 接口 POST /api/matches → 返回 400，提示用户先完成分析（不自动补齐）
       Agent 工具 matchResumeToJob → 工具内部先补齐缺失的分析，再继续
  → MatchService 按固定权重计算匹配分数（不调用模型）
  → 模型仅负责生成解释与建议
  → 保存 match_record
  → 返回匹配报告
```

评分由后端确定性规则计算，模型负责解释和提出建议。评分权重放入配置，不得让模型直接返回总分。

**两条入口的差异是有意设计**：REST 接口面向用户直接操作，让用户显式决定分析时机、避免一次请求内串联多次模型调用（耗时与成本不可控）；Agent 工具面向对话场景，由助手代为补齐更符合交互预期。两者最终都保证 `match_record` 的分析依据非空（见数据库设计文档 5.8）。

### 6.3 Agent 工具调用

```text
用户请求
  → AgentController 校验身份与请求
  → JobAssistantAgent / ChatClient
  → 模型判断是否调用工具
  → 后端执行已注册 Tool（受最大调用次数与总超时约束）
  → Tool 调用对应 Service
  → 工具结果返回模型
  → 模型生成最终答复
  → 保存会话消息与工具调用摘要
```

**【已核实】DeepSeek 侧的关键约束**：DeepSeek 当前模型默认开启思考模式，而思考模式与 Tool Calling 组合时有强制协议要求（携带 `tools` 的请求必须在后续请求中回传 `reasoning_content`，否则返回 HTTP 400），且思考模式下 `temperature` 等参数不生效。

因此本项目约定：**Agent 工具调用统一使用非思考模式**，通过 Spring AI 2.0.x 的 `spring.ai.deepseek.chat.thinking.type=disabled` 关闭思考模式。配置方式与依据见 Agent 设计文档第 7 节。

**【待验证】** `Thinking.DISABLED` 下的 Tool Calling 完整闭环（含多轮工具调用）必须通过 PoC 实测确认，这是项目初始化后的第一项技术验证。

## 7. 安全设计

1. 密码使用 BCrypt 存储；密码长度不少于 8 位且同时包含字母与数字。
2. JWT 使用 **HS256** 算法与高熵密钥（不少于 32 字节 / 256 bit），设置过期时间；密钥放环境变量，不写入仓库。
3. 用户资源查询必须带上 `user_id` 条件，例如 `WHERE id = ? AND user_id = ?`。
4. 文件名采用服务端生成的随机名称，不能直接将用户文件名拼接为磁盘路径。
5. 校验文件大小、扩展名、MIME 和文件魔数；禁止执行上传文件。
6. 对模型输入做长度限制，模型输出按 DTO 和业务规则校验。
7. 日志不记录密码、JWT、API Key 或完整敏感简历内容。
8. 删除简历时按既定策略同步处理原文件和关联数据（策略见第 7.1 节与数据库设计文档 5.4 节）。
9. 对外部模型 API 设置合理超时和异常提示。
10. 对用户提交的简历内容视为不可信数据，Prompt 中明确它只是待分析材料，不是系统指令。
11. **工具返回内容同样视为不可信数据**：工具返回的简历分析结果等文本会再次进入模型上下文，系统提示词须明确其不构成指令。

### 7.1 文件存储规则

存储路径在配置中定义（`app.file.storage-root`），且**必须位于项目运行目录之外**，目录结构固定为：

```text
{storage-root}/{userId}/{uuid}.{ext}
```

实现要求：

- 文件名由服务端生成（UUID），不使用用户上传的原始文件名。
- 写入前对拼接后的绝对路径执行 `Path.normalize()`，并校验结果仍位于 storage-root 之内，防止路径穿越。
- 数据库 `file_path` 字段保存相对于 storage-root 的路径，不存放本机绝对路径。
- 简历逻辑删除时同步物理删除该文件。

### 7.2 跨域（CORS）配置

前端 Vite 开发服务器与后端端口不同，必须配置 CORS：

- 开发环境：允许来源 `http://localhost:5173`，允许方法 `GET/POST/PUT/DELETE/OPTIONS`，允许头 `Authorization, Content-Type`，允许携带预检缓存。
- 生产环境：前端构建为静态文件后由 Nginx 或后端静态资源服务提供，前后端同源，**关闭跨域配置**。
- 允许来源写入配置项，不得在代码中硬编码 `*`；由于认证使用 `Authorization` 头而非 Cookie，无需开启 `allowCredentials`。

### 7.3 Token 存储约定

- 前端将 JWT 存放在 `localStorage`，请求时通过 `Authorization: Bearer <token>` 头携带。
- 该方案对 CSRF 天然免疫（不使用 Cookie），但需注意 XSS 风险：前端不渲染未经过滤的用户 HTML，简历文本展示一律使用文本节点。
- 后端不实现 Token 撤销机制，退出登录由前端清除 Token 完成（接口说明见 API 接口设计文档）。

## 8. 异常处理约定

| 场景 | HTTP | 业务码 | 处理方式 |
|---|---:|---:|---|
| 参数不合法 | 400 | 40000 | 返回字段级错误信息 |
| 参数校验失败 | 400 | 40001 | Bean Validation 错误 |
| 未认证/Token 无效 | 401 | 40100 | 不区分"未登录"与"Token 过期"细节 |
| 无权访问资源 | 403 | 40300 | 或按安全策略统一返回 404 |
| 资源不存在 | 404 | 40400 | — |
| 文件类型不支持 | **415** | **41500** | 扩展名、MIME、魔数三者均需校验 |
| 文件过大 | 413 | 41300 | 需在全局异常处理器中映射 `MaxUploadSizeExceededException`（默认返回 500） |
| 请求过于频繁 | 429 | 42900 | 第一版仅对 AI 相关接口做简单频率限制；若不做限制则移除该错误码 |
| AI API 超时/不可用 | 502 | 50200 | 允许用户重试，响应中说明可重试 |
| AI 输出无法解析 | 502 | 50201 | 不保存无效结果，记录脱敏错误并提示重试 |
| 未预期异常 | 500 | 50000 | 响应中不泄露堆栈 |

**状态码统一说明**：V1.0 中"文件格式不支持返回 400"与 API 文档的 415 相互矛盾，V1.1 统一为 **415**。

## 9. 部署结构

开发环境：

- 前端：Vite 开发服务器（`http://localhost:5173`）。
- 后端：Spring Boot 本地运行（`http://localhost:8080`）。
- 数据库：本机 MySQL 8.x。
- 文件：项目运行目录之外的本地目录。
- 模型：调用 DeepSeek 远程 API。

生产/演示部署：

- 前端构建为静态文件，由 Nginx 或后端静态服务提供，与 API 同源。
- 数据库密码、JWT 密钥和 DeepSeek API Key 通过环境变量或本地未提交的配置文件注入。
- `.gitignore` 必须包含 `application-local.yml`、`*.env`、上传目录等条目。

## 10. 第一版验收标准
